Pipeline lab: six stages, one instruction per clock

Load a program, press Step, and watch each instruction move FETCH1 → FETCH2 → DECODE → EXECUTE → MEMORY → WRITEBACK. This page runs the same cycle-exact model the SystemVerilog in src/ is tested against.

    Who is running?

    This program shares the CPU between several parts (its # REGIONS: line names them). Each row is one part, time runs left to right over the whole run, and every cycle belongs to the last instruction that reached WRITEBACK. The line is now.

    Pipeline chart

    Rows are instructions in fetch order, columns are clock cycles. Hatched cells are held by LOAD_STALL, grey rows were fetched down a wrong path and squashed, a ring marks an operand forwarded into DECODE.

    Branch prediction
    
      
    FETCH1 reads four tables every cycle. The tournament chooser picks, per branch, between a per-branch history table (BHT) and gshare; the branch target buffer (BTB) remembers where taken branches went so FETCH1 can jump there at once; FETCH2 takes return addresses from the return address stack (RAS).
    
      
    
      
    
        
    GLOBAL_HISTORY_REGISTER (newest on the right)
    
        
    00 strong NT01 weak NT10 weak T11 strong T
    
      
    
      
    
      
    
        
    BHT: 128 two-bit counters, one per branch address
    
        
    Chooser: dark = trust gshare, light = trust the BHT
    
      
    
      
    
        
    BTB: 16 entries
    
        
    RAS: 8 return addresses
    
          
    Without a BTB hit, FETCH2 still computes PC + imm from the instruction bits and redirects FETCH1, at the price of one bubble.

      Performance
      
      
      
      
      cycles = N + 5 + L + 3F + R + K + I + D + X: instructions, 5 to fill the pipeline, 1 per load stall, 3 per flush, 1 per surviving FETCH2 redirect, the multiply/divide busy cycles, the instruction and data cache miss cycles, and 1 per interrupt. The page checks this identity when the program halts (docs/MATH.md).
