Why gaps appear

  • Flush: a wrong guess or a ret, 3 cycles lost
  • Redirect: a taken branch or jal seen in FETCH2, 1 cycle
  • Load stall: data not back from memory yet, 1 cycle
  • Pipeline filling up at the start, 5 cycles
  • Instruction cache miss: waiting for main memory
  • Data cache miss: a load waiting for its line
  • Multiply or divide still working

A shorter critical path, and fewer wasted cycles.

The baseline computes a whole 64-bit division in one clock cycle: 64 subtractions in a row, 133 ns. The performance edition divides one bit per cycle, adds carry-lookahead (Kogge-Stone) adders, and wins cycles back with a tournament branch predictor, a branch target buffer, a return address stack and precise load stalls, behind instruction and data caches with prefetching. Both designs are in the repository and both are checked cycle by cycle.

Why not higher? In 130 nm one carry step of an adder takes about 330 ps; in 7 nm the whole core's longest path is 748 ps. Smaller processes are faster, but a process node is chosen by the foundry, not written in RTL. How every number was measured.
