Five branch predictors, one race.

Every conditional branch a program runs is replayed through five predictors, from a simple per-branch table to the families inside today's CPUs: a perceptron (a tiny neural network per branch, like AMD's Zen) and TAGE (tables looked up with longer and longer histories, used in AMD Zen 2 onward, Intel and ARM cores). Each guesses before it is told the answer. Try predictor challenge: one of its branches depends on the two branches before it.

gshare and the tournament are built in Sixfold's SystemVerilog; the perceptron and TAGE are software models (model/predictors.js), the way architects try a predictor before building it.

Inside the caches.

Main memory needs 10 cycles to deliver anything, so Sixfold keeps two small, fast copies next to the pipeline: 4 KiB for instructions and 4 KiB for data, each 64 sets of two 32-byte lines. Every address is cut into three fields: the tag says which piece of memory, the set index picks one of the 64 sets, the offset picks the byte inside the line. Each set can hold two lines (top half: way 0, bottom half: way 1); when both are full the one used longest ago is replaced. After each miss, both caches also fetch the next line on their own (prefetching, as every modern CPU does).

Bit tricks: one instruction instead of a loop.

Sixfold implements Zba and Zbb, the bit-manipulation extensions every current RISC-V application processor has. Counting the 1 bits of a register takes a 64-trip loop in plain RV64I and one cpop here; finding the end of a string goes 8 bytes at a time with orc.b. Pick an operation and a value: the result comes from the same model code that is checked against the RTL.

Inside the multiplier: carries that never wait.

Adding 16 shifted copies of a number one after another would make each one wait for the carries of the last. A Wallace tree adds them in columns instead: every group of three rows goes through a row of full adders and comes out as two (sum bits stay put, carry bits move one column left). Rows shrink 16, 11, 8, 6, 4, 3, 2 and no carry ever travels far until one final add.

Sixfold's step does 64 x 16 bits plus a running total kept as two numbers, every clock cycle: src/Carry_Save_Multiplier.sv. That change moved the multiplier off the critical path (747 ps to under 523 ps at 7 nm).

A shorter critical path, and fewer wasted cycles.

The baseline computes a whole 64-bit division in one clock cycle: 64 subtractions in a row, 133 ns. The performance edition divides one bit per cycle, multiplies with a Wallace tree, adds carry-lookahead (Kogge-Stone) adders, and wins cycles back with a tournament branch predictor, a branch target buffer, a return address stack and precise load stalls, behind instruction and data caches with prefetching. Both designs are in the repository and both are checked cycle by cycle.

Why not higher? In 130 nm one carry step of an adder takes about 330 ps; in 7 nm the whole core's longest path is 523 ps; 2.5 GHz needs 400 ps and 5 GHz 200 ps. Smaller processes are faster, but a process node is chosen by the foundry, not written in RTL. How every number was measured.
